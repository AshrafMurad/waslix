# M8.8 · Docker, Coolify and deployment

## Outcome

M8.8 owns the repeatable production deployment path for the existing Waslix release candidate: one Docker image that can run the web process or the worker, PostgreSQL through a persistent volume, reviewed migrations as a release step, optional demo seed execution, web/worker health checks and operator smoke/restore checks.

## Production services

| Service | Command | Purpose |
| --- | --- | --- |
| `web` | `npm run start` | Next.js production server on port 3000. |
| `worker` | `npm run worker:start` | pg-boss dispatcher, health sweep and intelligence refresh worker. |
| `postgres` | Postgres image | Primary production database with persistent volume. |
| `migrate` | `npm run db:migrate` | One-off release step; do not run concurrently from every app container. |

## Required environment

Set these values in Coolify secrets/environment, not in source control:

- `DATABASE_URL`: internal PostgreSQL URL, for example `postgresql://waslix:<password>@postgres:5432/waslix?schema=public`.
- `POSTGRES_PASSWORD`: database password used by the managed compose Postgres service.
- `BETTER_AUTH_URL`: public HTTPS app URL.
- `BETTER_AUTH_SECRET`: at least 32 random characters.
- `NEXT_PUBLIC_APP_URL`: public HTTPS app URL used by browser-visible links.
- `SEED_FIXTURE_PASSWORD`: required only when running the production demo seed.
- `WORKER_HEARTBEAT_FILE`: optional; defaults to `/tmp/waslix-worker-heartbeat`.

## Coolify deployment

1. Create a Docker Compose resource from `docker-compose.production.yml`.
2. Configure the public domain on the `web` service and enable HTTPS/TLS in Coolify.
3. Store all required environment values as Coolify secrets. Do not commit a production `.env` file.
4. Deploy the `postgres` service first and confirm its health check passes.
5. Run the release migration once with the `release` profile: `docker compose -f docker-compose.production.yml --profile release run --rm migrate`.
6. Deploy or restart `web` and `worker` from the same image.
7. Confirm `web` health is green through `/api/health/ready` and the `worker` health check sees a fresh heartbeat file.

## Seed strategy

Demo data is deliberate, not part of every deploy. For a public demo workspace, set `SEED_FIXTURE_PASSWORD` to a generated non-public password and run `npm run db:seed` once after migrations. Re-running seed must remain scoped to the fixture workspaces owned by the seed system; do not run seed against arbitrary customer production workspaces unless intentionally rebuilding the demo fixture.

## Smoke checks

After every deployment, run:

```bash
DEPLOYMENT_SMOKE_URL=https://your-domain.example npm run smoke:deployment
```

The smoke command verifies the live endpoint, database readiness endpoint and English sign-in page. Then manually verify sign-in, workspace selection and one protected overview page with a permitted demo account.

## Database backup and restore check

Before public production release, verify backup and restore on a disposable database:

1. Create a backup from the production database: `pg_dump "$DATABASE_URL" --format=custom --file=waslix-release.dump`.
2. Restore into a disposable database: `pg_restore --dbname "$RESTORE_TEST_DATABASE_URL" --clean --if-exists waslix-release.dump`.
3. Point a temporary Waslix container at `RESTORE_TEST_DATABASE_URL` and run `npm run db:migrate`.
4. Start the web container against the restored database and run `DEPLOYMENT_SMOKE_URL=<temporary-url> npm run smoke:deployment`.
5. Delete the temporary database and dump after the restore result is recorded.

## Operational notes

- Keep a reverse proxy in front of the Next.js server; Coolify provides the public HTTPS proxy.
- Use one migration run per release. Application rollback does not automatically roll back destructive database changes.
- The current deployment is a single web instance plus one worker. Add shared cache coordination before scaling web horizontally.
- Logs must keep operation/job IDs and workspace context safe; do not log credentials or customer narratives.
